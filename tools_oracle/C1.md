# Float operand order (C-num class) - notes (10-21, ora)

c1xx.dll was NOT reverse-engineered yet; this file holds the empirical data so far.
Case: CG_DrawPlayerCompass 0x4bf100 (12 lines). Retail h line: `fld size; fmul rect->h`; ours
`fld rect->h; fmul size`. Retail w line: `fld rect->w; fmul size` (same as ours).

PINNED (go.sh fast relinks, main source x,y,w,h order):
- Operand spelling never matters: `rect->h * size` / `size * rect->h`, y line `(size-1)*rect->h` /
  `rect->h*(size-1)` (pc0-3), local decl order of x/y/w/h (pd1-4): all 12 lines, identical.
- c2's linearisation never swaps float ops (SCHED.md round 4), so the order arrives from c1 or from the
  x87 lowering.
- Statement order DOES move it (h line, which operand is loaded first):
  | order | h line | lines |
  |---|---|---|
  | x y w h (main) | rect->h first | 12 |
  | x w h y (po1) | size first (retail form) | 28 |
  | w h x y (po3) | size first | 28 |
  | h x y w (po4) | size first | 22 |
  | x h y w (po2) | rect->h first | 25 |
  So the choice depends on which expressions were referenced earlier in the fn (value-number / CSE
  history), not on the statement's own spelling. Retail keeps x y w h (the other lines match) yet gets
  size first, so the difference is an earlier reference of size or rect->h (HYPOTHESIS: in the y line or
  before it, e.g. the fade/alpha code reading the dvar).
- Dead shapes: `float size` local (73 lines), local dvar pointer (12), `float rh = rect->h` (23).

Round 6 (operands of the moved tuple):
- tiny/ops.py over a T-hook dump that also printed the 3 operand objects (+0x28/+0x2c/+0x30, 6 dwords):
  operand objects carry a kind at +4: 0x24f (most register/temp operands), 0x250, 0x251, 0x252, 0x24b
  (constant), 0x259 (call target). Block 2 of the compass pair = fmul (0x63, two 0x24f operands), the
  0x2d tuple (two 0x24f operands, td adds a third 0x2c4 operand), call (0x0e, 0x259 target), 0x0d. The
  IL here is already machine-level (post-lowering), so 0x2d is a register-to-register op next to the call;
  its source construct is still not named.

Round 8 (scale's definition):
- Retail vs ours CursorHint (side by side, s24.sh): identical code except the two `rect->h + scale` sites.
  scale = [esp+0x18] in both (0 in the >=3 arm, fstp'd from the formula otherwise), halfscale [esp+0x14];
  the slot 0x18 is reused in the text arm for the (float)UI_TextHeight fild temp in BOTH. So scale's
  definition path is the same in retail and ours; nothing to copy from retail's asm.
- Minimal LTCG probes (tiny/scank2.sh): `rect->h + s` loads the FIELD first only when s is itself a
  pointer-deref value (m2: `s = c[1]`, no call between); once s lives in a stack slot (after a call, a
  branch, a global, a cast) the stack value is loaded first. Retail CursorHint loads the field first with
  scale in a stack slot, which these rules do not produce.
- Aggregate scale (float[2] / struct {half, full}) in the real fn: 98-113 lines and still scale first.
- 6 more clone shapes (local copies of rect->h or scale, `(*rect).h`, `rect[0].h`, a float* cast) keep it.
